# 统一安装与快速更新程序设计

日期：2026-11-13。状态：用户已明确统一入口、流畅更新和旧版兼容目标；跨项目实施方案待确认，尚未实现或发布。
涉及项目：iyw-claw-installer、iyw-claw、iyw-fusion-api。

## 目标与验收

1. 对外提供同一个安装与更新程序；新电脑完成安装，已有应用进入更新模式并保留安装位置。
2. 更新以组件身份与入口检查为主；环境未变时不下载、不解包、不全量扫描环境目录。
   仅应用版本变化不能触发全环境修复；缺失或不匹配组件单独补齐并验证。
3. Fusion 管理端控制更新补装、停止新增、明确移除，策略按目标应用版本和平台生效。
4. 已发布客户端继续通过原来的 Tauri 接口和制品完成升级；旧安装向导也能继续安装稳定版。
5. 下载、验签、环境准备或部署失败时不报成功；保留可恢复状态、诊断和用户数据。

“后端新增或减少”暂按后台控制受管环境组件解释。默认建议区分停止新增与明确移除，
这是待确认的产品决策。新增任意类型组件仍需客户端具有对应的可信安装配方。
本次覆盖现有桌面平台，不扩展 Windows/Linux/macOS 支持版本，也不改变 server 自更新。

## 本轮实施边界与兼容底线

2026-11-13 用户再次要求安装与更新统一，并特别强调兼容旧版本。
本节明确本轮的最小交付范围；下文环境 v2、数据库策略和显式退役属于后续可选扩展，
不因统一入口而默认授权实施。

- 保留环境 v1、业务检查接口、Tauri 原生 manifest/204、签名公钥和完整安装包。
  旧客户端的包 URL 仍指向其能够安装的完整制品，不能换成独立向导。
- 先发布包含统一向导的过渡应用版本。0.1.333、0.1.334 等旧客户端按原流程升级一次，
  此后再由应用调用统一向导；旧安装向导保持原用法。
- 统一向导增加显式更新模式，继承应用选定的版本、发布 ID、通道、安装目录和缓存。
  它不能重新选择 stable 最新版覆盖用户已经选定的版本，也不能静默降级。
- 使用现有环境事务和安装清单，跨应用版本也按组件身份、事务回执和入口快检复用。
  健康更新不执行全量 diagnose/repair；新下载内容仍完整校验，显式修复继续全量校验。
- 后台新增或减少组件先复用当前发布绑定与安装策略。“减少”默认停止新增，
  不凭清单省略或组件禁用删除已有内容；真正卸载、数据库新字段和环境 v2 另行确认。
- 应用的检查更新、提示、下载进度和任务空闲保护保持现有入口，实际部署交给同一个向导。
  向导沿用现有界面，并识别安装/更新模式，避免用户再次选择安装位置。
- 新向导不可用、能力不匹配或平台尚未就绪时，在部署开始前保留原更新链路。
  启动部署之后发生失败则按原事务恢复，不并行启动另一条更新链路。
- 主程序、技能、会话、项目、配置和运行环境的现有所有权边界不变；
  更新仅替换应用区域，新增组件只写本产品受管目录。

过渡版本号在发布时确定，不移动现有 0.1.334 标签，也不改写已经交付的签名包。
桌面构建继续由 CI 或指定发布环境完成；本机不编译 iyw-claw 桌面端。

| 用户现状 | 更新入口 | 预期行为 |
| --- | --- | --- |
| 已安装旧应用，没有新向导 | 原应用内更新 | 下载原格式的签名完整包，升级到过渡版本 |
| 已安装过渡版本或更新版本 | 原应用内检查更新 → 统一向导 | 复用选定版本、目录和缓存，执行快速环境检查 |

## 现状依据

- `src/main.cpp` 只有安装向导入口，尚无应用调用的更新模式和交接协议。
- `src/installer.cpp` 编排系统检查、版本查询、环境计划、下载安装和完成检查。
- `src/release.cpp` 固定查询 stable 的 `0.0.0`，适合手动安装和回退，不适合直接承接
  客户端已经选定的 beta、灰度或特定版本更新。
- `src/environment_inventory.cpp` 已按版本、versionId、artifactId、SHA-256 身份、
  事务回执与入口状态检查已安装环境，可保留现有轻量路径。
- `src/environment.cpp` 的 Compatible 还要求 pcVersion 相等；不同版本可能进入 repair，
  修复结束又调用 diagnose。不能简单放宽比较后跳过库存提交，否则目标版本清单仍过期。
- `iyw-claw/src-tauri/environment-core/src/install.rs` 已区分普通 prepare 与 full_check 修复；
  `prepare_repair` 跨 pcVersion 会恢复完整集合，diagnose 会逐个完整校验组件。
- 环境助手和 NSIS 已有准备、提交及回滚路径，应沿这些边界扩展，避免向导再建安装事务。
- `iyw-claw/src-tauri/src/update/desktop.rs` 由 Tauri updater 下载、缓存和安装，已有后台
  更新状态、任务空闲保护与重启逻辑；`release_windows.rs` 已保留安装目录。
- Fusion 的环境 v1 仅支持 keep/install/update；旧向导解析每个 action 都要求 artifact。
  `installOnInitialize=false` 只抑制未安装组件，已有库存仍允许维护，不表示卸载。
- Fusion `environment_binding.go` 还包含编译内置组件集合；只改管理界面无法让新组件进入绑定。
- Fusion 的应用业务检查接口与 Tauri 适配接口共享选择逻辑，但响应形状不同，均需保留。

## 统一程序与客户端交接

同一可执行程序支持安装与更新模式。直接打开时探测已安装应用及真实目录；没有应用则安装，
已有应用默认更新。应用内发起更新时，携带当前受信发布记录、channel、安装位置和更新意图，
进入更新进度页，无需重新选择目录。

应用继续负责检查更新、用户偏好、灰度、跳过版本和活动任务保护。选定版本后由统一程序执行
实际部署；交接时保持 releaseId、目标版本、平台、架构与摘要一致，不重新选择一个最新版本。
统一程序复核服务端发布状态与制品签名，拒绝任意命令、脚本和不受信下载来源。

沿用现有预下载缓存，统一程序复核缓存身份后复用，不能再下载一次完整主包。
首次独立打开仍使用稳定版安装规则；客户端指定通道时保留其语义。环境绑定目前仅支持 stable，
beta 更新不得偷偷改用 stable 环境计划；缺少准确绑定时保留原更新链路，待相应绑定可用再启用。

统一程序随新版应用携带，运行前复制到应用目录之外的版本化临时目录并验签，避免自身被覆盖。
公开下载入口提供最新版统一程序；内部完整应用包继续作为安装负载和旧客户端更新制品。
当前版本无法理解新组件配方时，要求先更新到支持该配方的正式助手，不执行后台传入的安装命令。

应用保存恢复位置并正常退出；更新程序等待指定应用及其受管子进程释放文件。
用户仍有活跃任务时沿用现有阻止或延期机制，不扩大强杀范围。更新完成才允许启动目标应用。
自动静默更新保留现有开关与空闲保护，错误写入可追踪结果，不能因引入新程序而变成强制弹窗。

## 快速环境处理

1. 快速检查平台、事务回执、组件身份、安装目录、入口存在性和入口大小。
2. 对照目标版本绑定生成 keep/install/update；显式退役计划须另行批准扩展后才启用。
3. 身份和入口匹配则直接复用；版本缺失、入口丢失或制品不同只处理该组件。
4. 复用现有缓存和并发上限：主包最多三路，环境最多两包；摘要校验和解包保持受控。
5. 在既有环境事务中更新目标 pcVersion、组件集合和回执；只变应用版本也要正确提交新库存。
6. 最终检查目标集合和新安装项，不无条件再调用全量 diagnose。显式修复继续保留完整校验。

健康路径不得扫描每个文件或执行每个工具的慢探针。轻量检查不能保证发现非入口文件损坏及
同大小内容篡改；该边界与当前安装向导一致。新下载字节仍需完整大小、摘要和签名校验。
NSIS 已负责环境准备，外层向导应复用其结果和回执，避免内外重复执行环境事务。

## 后台策略与兼容协议（后续可选扩展）

本节描述未来扩展，独立于本轮统一入口；本轮不新增数据库字段，也不默认启用显式卸载。

保留现有 `installOnInitialize` 含义，新增独立的更新补装策略；管理员可对更新用户开启或关闭
新组件补装。依赖约束优先：目标应用必需组件不能被配置成缺失，否则拒绝发布该组合。

停止新增只影响尚未安装的组件，不等同卸载或停止维护。明确移除是独立策略，限定目标应用
版本、平台与架构；不凭清单省略、网络错误、disabled 或空响应推断删除。

建议通过环境 v2 resolve/download 承载新策略，沿用现有 POST 和业务响应包装；v1 行为保持。
v2 接收真实库存、目标应用上下文及助手能力，返回明确的保留、补装、更新与退役意图。
退役条目独立于制品下载 action，避免要求不存在的 artifact。老客户端仍使用 v1。
v2 未部署时，新程序只能回退到 v1 的非破坏性安装维护，不能猜测或执行移除。

更新补装开关与退役策略需要持久化、审计和 catalog revision 刷新。实施时在现有
agentrelease domain/application/adapter 分层和统一管理页中增加最小字段及配套迁移，
并同步 GORM、SQL、协议文档。属于共享契约和数据库改动，实施这项扩展时必须单独确认。
组件目录和 PC 版本绑定一起校验：客户端支持的已有组件可以后台增减；未知组件类型需要
发布客户端配方。保留已停用本地模型架构的限制，不恢复独立技能仓库更新。

移除只能作用于本产品库存登记的受管目录，检查路径归属、符号链接和依赖引用；不能删除
系统 Node/Git/Python、用户配置、会话、项目、外部工具或其他安装仍使用的组件。
部署时先停用并保留事务备份；失败恢复旧库存和原组件。成功后回收不再被有效库存或回滚
引用的受管目录；文件被占用时记录延期清理，不把失败清理伪装成已经释放磁盘。

## 旧程序升级与发布顺序

1. 后端增加兼容能力，原 v1、Tauri 原生 manifest、204 语义、签名和旧制品保留。
2. 发布包含统一更新程序及新环境助手的正常完整应用版本，作为迁移入口。
3. 老应用继续按原流程下载签名完整包并升级到该版本，随后具备新的更新入口。
4. 新客户端按能力启用统一程序，公开下载入口改为统一程序；旧向导仍可查询稳定版完整包。
5. 后台退役策略只对支持它的新助手生效，不能把 remove 塞进旧 v1 响应。

新版本可以长期保留旧链路回退，不要求所有存量用户在同一时间升级。
禁止直接把 Tauri manifest 的旧包 URL 换成普通引导 EXE；跨平台还涉及包格式、签名及安装语义。
平台缺少新入口或正式制品时保持原更新能力，不能错误返回成功或选择其他平台制品。

## 失败、恢复与验证

正式部署之前完成下载校验与环境准备。部署中的失败沿既有事务恢复应用和库存；跨进程中断
由事务回执识别，重试不得重复激活或误删组件。外层环境检查失败时也要覆盖恢复路径，不能
只依赖内层 NSIS 已成功的退出码。无需全局重构部署架构。

| 场景 | 验收证据 |
| --- | --- |
| 健康环境更新应用 | 环境下载、解包、全量散列次数均为零，库存更新到目标应用版本 |
| 缺一个组件或入口 | 仅补该组件，最终检查通过；其余组件无重复安装 |
| 后台新增组件 | 只对目标版本及支持平台生效，关闭更新补装时符合依赖约束 |
| 停止新增、明确移除 | 前者保留已有内容；后者仅退役受管目标，失败可恢复 |
| 老客户端、老向导 | 原接口及包仍可用，能升级到迁移版本，无签名或参数破坏 |
| 取消、断网、过期计划、损坏包 | 不提交半成品，保留错误原因并可重试 |
| 活跃任务、重复点击、文件占用 | 延期或拒绝冲突操作，不出现两个并行部署事务 |
| 平台差异 | Windows/Win7、macOS、Linux 对应制品与助手身份匹配 |

性能记录分别统计本地快检、计划请求、下载、部署和提交耗时；同机同库存对比更新前后多次样本，
以零重复下载和零全量扫描作为稳定验收，不把网络速度混入快检性能结论。
安装向导做 Release 构建和隔离流程验证；Fusion 做相关契约/策略回归、编译及仓库要求的 smoke；
iyw-claw 默认规则禁止测试，需在本方案批准时明确授权本次安装更新相关定向测试。
正式平台升级/回滚实测和制品签名验收单独记录，不能用本机编译代替。
